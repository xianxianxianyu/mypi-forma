# 路线图：从人的问题到领域可视化

[← README](../README.md)

## 当前起点

已实现的是一个本地对话应用：OpenUI 渲染 53 个注册组件定义，transitions.dev 为提交后的 UI 提供构建动画，assistant-ui 管理聊天；默认 Pi · DeepSeek Flash 负责生成，可切换 Codex。侧边栏提供金融示例提示，项目已有组件设计与动画接入 Skill。通用组件和提示并不代表已经具备经过验证的金融或其他行业图表引擎。

**下面的通用可视化方法及领域图表包属于计划，不是已交付能力。** 候选领域不是交付承诺；优先级由真实案例、数据可得性与可验证价值决定。

## 主线一：Agent 可视化方法

目标不是「收到一句话就猜一张好看的图」，而是让 Agent 有一套可解释、可验证的过程：

1. **理解问题**：谁会看？需要做什么判断？哪些信息最重要？
2. **确认数据**：数据来自哪里？粒度、单位、时间区间、统计口径是否明确？缺失时先问，不编造。
3. **选择表达**：比较、趋势、分布、关系、组成、流程，各自适合怎样的图形？什么时候应该用表格或文字？
4. **设计阅读顺序**：标题、指标、图例、注释、交互如何协同，而不是争夺注意力？
5. **设计有意义的动态**：动画解释层次或变化，而不是假装推理进度、掩盖数据问题。
6. **验证结果**：数据是否失真？长标签、空数据、极端值、键盘操作、减少动态效果是否成立？

计划交付：

- 原创、可复用的 Agent Skill 与选择规则。
- 「用户问题 → 澄清 → 数据契约 → 视觉表达」成对示例。
- 含错误选择、缺失数据和反例的评估集。
- 能验证问题是否被回答的标准，而非只比较截图是否漂亮。

现有 `skills/mypi-forma/` 是开发规范的起点；运行时目前仍通过注册组件生成提示，并不自动执行这些未来 Skill。

## 主线二：垂直领域图表

候选案例，**目前均未作为专用组件实现**：

| 领域 | 需要回答的问题 | 候选表达 | 必须明确的语义 |
| --- | --- | --- | --- |
| 增长 / 电商 | 用户在哪里流失？ | 转化漏斗 | 去重、步骤顺序、窗口期、分母 |
| SaaS / 产品分析 | 不同批次用户是否持续回来？ | Cohort 留存矩阵 | cohort 定义、活跃口径、未成熟周期 |
| 项目 / 研发 | 什么依赖会影响交付？ | 时间线、依赖关系图 | 状态、依赖类型、时间基准 |
| 运维 / 性能 | 平均值是否掩盖尾部问题？ | 延迟分布、分位数趋势 | 单位、采样、聚合方式、异常值 |

### 一个领域贡献应包含什么

- 一个明确的业务问题，以及不适用的场景。
- 脱敏或合成数据和来源说明，不能上传客户/内部数据。
- 有界的数据契约：单位、粒度、口径、空值与异常数据处理。
- 注册组件及真实交互，不允许模型输出任意可执行代码。
- 图例、可访问说明和必要的非视觉信息。
- 动态规则：什么变化值得播放，何时保持稳定。
- Agent 使用指引、完整示例、契约和浏览器测试。
- 清楚的原创/第三方许可，不将受限动画代码重新包装为动画库。

## 建议推进顺序

1. 先把当前通用控件的示例、说明与评估标准做好。
2. 选一个数据与问题最明确的领域，完成从方法到组件的闭环。
3. 再提炼共性，避免一开始就做巨大的通用图表抽象。
4. 扩展第二个领域时验证复用方式；不要只复制视觉样式而忽略业务语义。

## 当前不承诺

- 任意 React/HTML 或任意图表生成。
- 实时外部数据接入、数据库连接或任意工具执行。
- 模型逐 token 绘图或通用几何变形动画。
- 多用户托管、持久化历史和生产级权限控制。

这些可以在需求明确后另行讨论，但不是当前项目定位成立的前提。
